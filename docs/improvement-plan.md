# Block Library — Improvement & Growth Plan
> Package: capell-app/block-library · Kind: package · Tier: free · Product group: Capell Foundation · Bundle: foundation · Status: Draft

## 1. Snapshot

`capell-app/block-library` is a **shared, foundation-tier registry/contract package**, not a catalog of rendered blocks. It ships no migrations, no admin resources, no Filament forms, no config, and exactly one Blade view — an empty `aria-hidden` fallback (`resources/views/blocks/fallback.blade.php`). The actual surface is: 3 Actions (`ListBlockDefinitionsAction`, `RegisterBlockDefinitionProviderAction`, `ResolveBlockDefinitionAction`), 5 contracts (`BlockDefinitionProvider`, `BlockRenderer`, `BlockFixtureProvider`, `BlockDemoContentProvider`, `FilamentBuilderBlock`), 12 Data objects (`BlockDefinitionData` + variant/setting/contract/screenshot/presentation/view-reference DTOs), 5 enums (`BlockBackground`, `BlockHeadingWidth`, `BlockMediaPosition`, `BlockSpacing`, `BuilderBlockTarget`), and 6 `Support` classes (`BlockRegistry`, `BuilderBlockRegistry`, `BuilderBlockDiscovery`, `BlockRegistryManifestCompiler`, `BlockRegistryManifestStore`, `NullBlockDefinition`). Deps: `capell-app/core ^4.0`, `filament/forms`, `lorisleiva/laravel-actions`, `spatie/laravel-package-tools` (PHP `^8.3`). Real consumers exist: `content-sections` registers a `BlockDefinitionProvider`, and `diagnostics` + `layout-builder` read the registry.

Marketplace summary (verbatim): *"Shared typed content block primitives and registration contracts for Capell packages."* Manifest `marketplace.screenshots` declares **1** image (`extension-card.jpg`). `docs/screenshots.json` declares **3** targets (all `required:false`). But `docs/screenshots/` contains **38 PNGs** named for ~18 rendered block types (hero, accordion, pricing, faq, testimonial, timeline, team, stats, logos, comparison, counter, tabs, table, features, divider, content, call-to-action) across admin + frontend. **The package ships none of those blocks** — those screenshots belong to a consuming package (almost certainly `content-sections`) and are orphaned here. `capabilities: []`, `performance.frontendRenderBudgetMs: 0`, `adminQueryBudget: 0`, `cacheSafety.cacheable: false`.

## 2. Improvements (existing functionality)

Prioritized.

1. **Wire up or delete the manifest-compile/store layer — it is entirely dead code.** `BlockRegistryManifestCompiler` and `BlockRegistryManifestStore` (the two largest, most defensive classes in `src/`, ~6.4KB combined: atomic writes, file locking, package-active + view-exists validation) are **never instantiated anywhere** — `grep` across all packages finds zero callers outside their own definitions. `NullBlockDefinition` and `PublicBlockPresentationData` are also unreferenced. The README's "Registry Cache Safety" section documents a compile/validate/fallback flow that **does not run**. Either (a) bind the store/compiler in `BlockLibraryServiceProvider::packageRegistered()` and route `ResolveBlockDefinitionAction` through the validated manifest with `NullBlockDefinition` fallback, or (b) delete the unused classes and the doc section. Shipping defensive code that is never executed is worse than not having it — it implies a safety guarantee that isn't enforced. — `src/Support/BlockRegistryManifestCompiler.php`, `src/Support/BlockRegistryManifestStore.php`, `src/Support/NullBlockDefinition.php`, `src/Providers/BlockLibraryServiceProvider.php` — **M**

2. **`ResolveBlockDefinitionAction` ignores the fail-closed fallback and throws a key-leaking exception.** It calls `BlockRegistry::getOrFail($key)`, which throws `InvalidArgumentException('Content block [%s] is not registered.', $key)`. The package built `NullBlockDefinition::make()` precisely for "when a registered block cannot be resolved safely," but the resolve Action never uses it. A consumer that calls this on a public render path will surface the raw block key in an exception. Make `ResolveBlockDefinitionAction` return `NullBlockDefinition::make($key)` (or a non-leaking variant) on miss, and reserve `getOrFail` for admin/dev contexts. — `src/Actions/ResolveBlockDefinitionAction.php:14`, `src/Support/BlockRegistry.php` (`getOrFail`) — **S**

3. **`BuilderBlockDiscovery` / `BuilderBlockRegistry` have zero external consumers.** `grep` for `BuilderBlockDiscovery`, `BuilderBlockRegistry`, `FilamentBuilderBlock`, `getBuilderBlockName` across all sibling packages returns nothing outside `block-library` itself (only its own tests exercise them). The discovery class is registered as a singleton in the provider but `registerDiscoverableBlocks()` is never called with paths, so it discovers nothing at runtime. Decide its fate: if `content-sections` is meant to expose Filament Builder blocks through it, wire that path and add an integration test proving the picker populates; otherwise mark it experimental or remove it. — `src/Support/BuilderBlockDiscovery.php`, `src/Support/BuilderBlockRegistry.php`, `src/Contracts/FilamentBuilderBlock.php` — **M**

4. **Add the diagnostics command the package's own docs ask for.** `docs/overview.md` → "Feature Suggestions" requests a command listing registered block definitions, providers, renderers, and missing views. `ListBlockDefinitionsAction` already returns `BlockRegistry::all()` but has no CLI/diagnostic surface. A `block-library:registry` Artisan command (delegating to the Action) makes the registry observable, gives `docs/screenshots.json`'s `block-registry-diagnostics-output` target something real to capture, and turns the shared package from a black box into a debuggable one. Register it in the manifest `commands` block. — `src/Actions/ListBlockDefinitionsAction.php`, `capell.json` (`commands`) — **M**

5. **`BlockRegistry::register()` hard-throws on duplicate keys with no override path.** Two packages registering `marketing.hero` will fatal at boot via `InvalidArgumentException`. For a shared foundation registry this is brittle — a single mis-keyed third-party block takes down the whole app. Add a deterministic conflict policy (first-wins + logged warning, or namespaced keys by `sourcePackage`), and surface conflicts through the diagnostics command rather than an uncaught boot exception. — `src/Support/BlockRegistry.php:18` — **S**

6. **Translate `NullBlockDefinition` and default-variant labels via keys, not hardcoded English.** `NullBlockDefinition::make()` hardcodes `'Safe fallback block'` and its description; the skill mandates user-facing strings use translations and the README's "Registry Cache Safety" section explicitly says labels should be translation keys resolved at render time. `resources/lang/en/blocks.php` exists but is barely used. Route these through `__()`/lang keys. — `src/Support/NullBlockDefinition.php`, `resources/lang/en/blocks.php` — **S**

## 3. Missing Features (gaps)

The manifest's `capabilities: []` is honest — this package advertises no capabilities — but that is itself the strategic gap for a "Block Library." Tied to block-catalog norms:

- **No actual blocks.** Despite the name and 38 block-type screenshots, the package ships zero block definitions and one empty fallback view. It is a *contract* library, not a *block* library. Table-stakes for anything called "block-library" in a CMS: a baseline set of registered, renderable blocks (rich text, image, heading, spacer/divider, CTA/button, embed). Today every block lives in `content-sections`; this package contributes nothing renderable. **This is the central positioning question (see §5).**
- **Responsive / spacing controls are modeled but not enforced or rendered.** `BlockSpacing`, `BlockHeadingWidth`, `BlockMediaPosition`, `BlockBackground` enums and `PublicBlockPresentationData` (variant/spacing/background/cardsPerRow/showCta/anchorId) exist as pure data with no renderer, no validation, and no Blade that consumes them. The vocabulary is defined; the behavior is absent.
- **Accessibility contracts are declarative-only.** `BlockAccessibilityContractData` and `BlockContentContractData` (requiredFields, maxItems, imageRatios, requiresCta, accessibilityRules) are DTOs that nothing validates against. There is no `ValidateBlockContentAction` enforcing the contracts a block declares — so the contracts are documentation, not guarantees. Differentiator opportunity: a shared content/a11y validator is exactly the kind of cross-cutting value a foundation package should own.
- **Block variants/presets modeled, never resolved.** `BlockVariantData` / `BlockVariantKey` support per-block variants and a default; nothing maps editor state → a chosen variant → a view. No `ResolveBlockVariantAction`.
- **No global/reusable-block concept.** No notion of a saved, reusable block instance shared across pages (a standard CMS block-library feature). Out of scope for a pure registry, but the obvious premium differentiator (see §5).
- **No block-content schema validation output.** The docs' own Feature Suggestions ask for schema validation so consuming packages catch missing labels/categories/preview-views/a11y metadata at registration time. `BlockDefinitionData`'s constructor validates a few non-empty fields and provider contracts, but there is no aggregate "validate the whole registry" reporting surface.

Table-stakes vs differentiator: shipping a baseline renderable block set + a content/a11y contract validator = **table-stakes** for the name. Reusable/global blocks, variant presets, and a visual block-preview gallery = **differentiators**.

## 4. Issues / Risks

- **Manifest ↔ asset mismatch (documentation/marketplace integrity).** `docs/screenshots/` holds 38 PNGs for ~18 rendered block types this package does not contain; `docs/screenshots.json` declares only 3 (registry-diagnostics, builder-picker, fallback-render), and `capell.json` `marketplace.screenshots` declares 1. The 38 PNGs are orphaned consuming-package assets. Risk: marketplace tooling or a screenshot runner keyed off the directory will publish misleading imagery implying this package renders heroes/pricing/FAQ. Either move those PNGs to `content-sections` or delete them; keep only the 3 declared (shared) captures. — `docs/screenshots/*.png` vs `docs/screenshots.json` vs `capell.json` — **High**
- **Health check is a no-op marker.** `BlockLibraryHealthCheck` implements only `compatibleCapellApiVersion(): '^4.0'` and probes nothing, yet the manifest registers it `severity: critical` with the label "surfaces, providers, and install health are discoverable by Diagnostics." (Sibling packages use the same minimal stub, so this is a platform pattern — not unique malpractice.) For a *critical* shared registry the check should actually assert something: e.g. the `BlockRegistry` singleton resolves and every registered definition's `publicView` exists. As-is, "critical" health is green even if the registry is broken. — `src/Health/BlockLibraryHealthCheck.php`, `capell.json` (`healthChecks[0].severity`) — **Medium**
- **Test coverage gaps on the highest-risk code.** Tests cover `BlockDefinitionData`, `BlockRegistry`, `BuilderBlockRegistry`, `BuilderBlockDiscovery`, manifest requirements, and a manifest test. But: (a) no test asserts public-output safety of `fallback.blade.php` (anonymous render leaks nothing — required by Capell skill rules for any rendering/cache change); (b) no test for `ResolveBlockDefinitionAction` miss behavior (the key-leak in §2.2); (c) `BlockRegistryManifestStore`'s atomic-write/lock path and `NullBlockDefinition` are untested *because they're dead*; (d) no test proving duplicate-key registration behavior is acceptable. — `tests/` — **Medium**
- **Public-output safety is structurally OK but unproven.** `BlockDefinitionData` carries `sourcePackage`, view names, and admin preview references; the `PublicBlockViewReference`/`AdminPreviewBlockViewReference` split is the right pattern to keep admin view names out of public output. But with no rendering pipeline and no anonymous-render test in this package, the guarantee rests entirely on consumers. The fallback view itself is clean (empty `aria-hidden` div, no metadata). — `src/Data/PublicBlockViewReference.php`, `src/Data/AdminPreviewBlockViewReference.php` — **Medium**
- **No XSS/rich-content surface here, by design — but the contract is unenforced.** Because the package renders nothing, there is no direct XSS exposure. The risk is downstream: `BlockContentContractData` implies rich fields but provides no sanitization helper, so each consumer re-solves escaping ad hoc. A shared escaping/sanitization contract would reduce per-package risk. — `src/Data/BlockContentContractData.php` — **Low-Medium**
- **Performance budgets are zeroed and meaningless.** `frontendRenderBudgetMs: 0` and `adminQueryBudget: 0` for a package that renders nothing is defensible, but `cacheSafety.cacheable:false` with empty `invalidationSources` should be revisited once blocks/manifest caching is wired — the manifest compiler exists to be cached but the manifest says nothing is cacheable. — `capell.json` (`performance`) — **Low**
- **i18n.** `resources/lang/en/blocks.php` is near-empty and hardcoded strings live in `NullBlockDefinition` (§2.6). Only `en` exists. — `resources/lang/en/blocks.php` — **Low**

## 5. Marketplace & Positioning

This is a **foundation, free, bundled** package (`product.tier: free`, `bundle: foundation`) — it is correctly positioned as platform plumbing, not a standalone purchase, and its `commercial.proposedLicense: free` / `requestedCertification: first-party` reflect that.

**Current `marketplace.summary`:** *"Shared typed content block primitives and registration contracts for Capell packages."* — Accurate but developer-jargon ("primitives," "contracts") and value-free to a buyer. **Composer `description`:** *"Shared typed content block primitives for Capell packages."* — duplicative, same jargon. The `capell.json` top-level `description` is a third, slightly different string ("shared typed block definitions and registration contracts"). Three near-identical descriptions should be unified.

**Improved summary (buyer-facing):** *"The shared foundation every Capell content block builds on — one typed contract for definitions, variants, accessibility rules, and safe public rendering, so block packages stay interoperable and fail closed."*
**Improved composer description (developer-facing):** *"Typed block-definition contracts, registry, and safe-fallback rendering primitives shared across Capell content packages (Content Sections, themes, builders)."*

**Free/bundle vs premium upsell.** Keep this package free and bundled — it is the integration seam that makes a *paid* block ecosystem possible. The monetization is adjacent, not here: a free, baseline block set ships against these contracts to prove the platform, while **premium block packs** (advanced marketing blocks, reusable/global blocks, A/B-variant blocks, the 18 block types whose screenshots are currently misfiled here) become the upsell built on top. Strengthening *this* package (real diagnostics, enforced a11y/content contracts, a validated manifest, proven public-output safety) directly raises the credibility of every paid block built on it. The pitch: *"every block in the marketplace shares one audited, accessible, cache-safe contract."*

**Screenshot/media gaps.** Remove the 38 orphaned PNGs (move to the package that renders them). Produce the 3 *declared* captures for real: registry diagnostics output (needs the §2.4 command), the Filament builder picker (needs a consuming-package harness), and the fallback render state (controlled fixture). A shared package legitimately has thin marketplace media — lean into "foundation" framing rather than borrowing a catalog's screenshots.

**How it strengthens the platform pitch.** It is the "open standard" story: third parties can ship blocks that drop into any Capell store because they all implement one typed, accessibility-aware, public-output-safe contract. That interoperability claim is only credible if the contract is *enforced* (§3 validator, §4 health check) rather than merely *declared*.
